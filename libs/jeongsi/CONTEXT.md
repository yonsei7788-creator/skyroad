# CONTEXT: 정시 분석 (libs/jeongsi)

> 수능 성적을 입력받아 대학별 환산점수를 계산하고 지원 전략 리포트를 만드는 모듈.
> 기존 생기부(수시) 리포트와 **독립된 상품**이며, `libs/report/` 에 의존하지 않는다.

---

## 1. 설계 의도

### 1.1 가장 중요한 원칙 — 계산은 코드, AI는 해설만

모든 수치는 **결정론적 코드**가 만든다. AI(Gemini)는 그 수치를 설명하는 **문장만** 쓴다.

환산점수·합격 가능성·상향/적정/안정 분류·순위·조합 구성은 AI가 **전혀 관여하지 않는다.**
이를 규약이 아니라 **구조로** 강제한다 — AI 응답 Zod 스키마에 숫자 필드가 **아예 없다.**
AI가 수치를 덮어쓸 경로 자체가 존재하지 않으며, 테스트가 이를 검증한다.

`libs/jeongsi/report-types.ts` 의 각 필드 주석에 `AI:` 마커가 있으면 AI가 채우는 필드,
없으면 코드가 채우는 필드다. **이 구분이 모듈 전체의 기준선이다.**

### 1.2 대학 환산식을 "코드"가 아니라 "데이터"로 표현한다

대학마다 반영비율·활용지표·영어/한국사 처리·가산점이 제각각이다.
이를 대학별 if 분기로 짜면 대학이 늘 때마다 코드가 늘어난다.

대신 `ConversionFormula` 라는 **데이터 스키마**로 환산식을 기술하고,
엔진 하나(`convert-score.ts`)가 그것을 해석한다.
대학 추가는 **JSON 한 줄 추가**이고 코드 변경이 없다.

### 1.3 데이터 출처를 로더로 격리한다

현재 입결·시행계획은 `data/*.json` 이지만, 향후 DB나 외부 API로 바뀔 수 있다.
`data/index.ts` 가 async 인터페이스로 이를 감싸므로 **호출부는 출처를 모른다.**

JSON은 `import` 하지 않고 **런타임에 `fs` 로 읽는다.** TypeScript 구조적 타입 추론을
타지 않기 위해서다. 기존 `libs/report/constants/admission-cutoff-data.ts` 가
11,757 엔트리에서 `TS2590` 으로 `@ts-expect-error` 를 단 전례가 있다.

⚠️ 경로는 **리터럴 상수만 조합**할 것. 런타임 변수로 만들면 Next.js 의 파일 추적이
깨져 Vercel 배포 시 JSON이 번들에 포함되지 않는다.

소비처:

- `app/jeongsi/` — 입력 폼, 생성 진행, 리포트 열람, 프리뷰

## 3. 사용 패턴

### 3.1 리포트 생성 (전체 흐름)

```ts
import { analyzeJeongsi } from "@/libs/jeongsi/engine/analyze";
import { buildJeongsiReport } from "@/libs/jeongsi/report/build";
import { JEONGSI_COMMON_SYSTEM_PROMPT } from "@/libs/jeongsi/report/system-prompt";

// 1. 코드가 모든 수치를 계산
const analysis = await analyzeJeongsi(input);

// 2. AI 는 해설 문장만 덧붙임
const content = await buildJeongsiReport(analysis, {
  reportId,
  geminiClient, // 옵셔널 — 없으면 해설을 건너뛰고 폴백 문구로 채움
  onProgress, // SSE 로 흘릴 진행률 콜백
});
```

`geminiClient` 가 없거나 AI 호출이 전부 실패해도 **리포트는 유효하게 나온다.**
숫자는 전부 코드값이므로 해설이 비어도 리포트로 성립한다. PART별로 독립 try/catch.

### 3.2 Gemini 클라이언트

`libs/report/pipeline/gemini-client.ts` 를 **수정 없이 재사용**한다.
`commonSystemPrompt` 가 파라미터라서 정시용 프롬프트만 주입하면 된다.

```ts
createGeminiClient({
  apiKeys: [env.GEMINI_API_KEY],
  commonSystemPrompt: JEONGSI_COMMON_SYSTEM_PROMPT,
});
```

모델 기본값은 `gemini-2.5-flash-lite`. **바꾸지 말 것** — gemini-client.ts 상단 주석에
"flash 는 503이 거의 100%"라는 실측 기록이 있다.

### 3.3 디자인 반복

`/jeongsi/preview` 에서 DB·AI 없이 목 데이터로 렌더링을 확인한다.
목은 기본 / 극단(결측·긴 이름·빈 슬롯) / 지원불가 / 의약 극상위 4종.

#### `notices` 는 추측하지 말고 뽑아 쓴다

`notices` 는 AI 가 아니라 코드가 생성한다 — `report/build.ts` 의
`buildRecommendationNotices()`. **목에 넣을 값은 그 함수를 실제로 돌려서 가져온다.**

```ts
// 해당 시나리오의 입력으로
const analysis = await analyzeJeongsi(input);
console.log(buildRecommendationNotices(analysis));
```

읽고 추론하지 말 것. 실제로 이런 일이 있었다 — "컴퓨터공학과·의예과는 정시 모집
대학이 많으니 `poolStage` 가 1일 것"이라고 추론해 빈 배열을 넣었는데, 샘플 데이터에서
**둘 다 2** 였고 확대 안내가 나왔다. 네 픽스처 중 셋이 틀렸다.

손으로 지어내면 **실제로는 한 번도 나오지 않는 텍스트로 레이아웃을 검증**하게 되고,
그렇게 작성된 목이 도메인 규칙(§6.1-e 다른 계열 대체 금지)을 어기는 문구를 담고
있던 적도 있다.

같은 이유로 `overallComment` 등 AI 필드도 **프롬프트가 허용하는 범위 안**에서 쓴다.
프롬프트가 막아둔 내용(재수 권유 등)을 목에 쓰면 다음 사람이 그것을 정답으로 본다.

## 4. 반드시 알아야 할 함정

### 4.1 분류 척도는 `percentileGap` 이지 `gapRatio` 가 아니다

환산 총점 대비 비율(`gapRatio`)은 **대학 간 비교가 불가능하다.**
백분위 1점당 환산점수 변화율이 서울대 1.583%, 인하대 0.750%로 **2.1배** 차이난다.
같은 "±1%"가 대학마다 전혀 다른 의미다.

분류에는 반드시 `percentileGap`(백분위점)을 쓴다. `gapRatio` 는 화면 표시용이다.

### 4.2 백분위 입결 비교에 `weightedPercentile` 을 쓰면 안 된다

공개 백분위 입결은 거의 전부 **국·수·탐 단순평균**이다.
대학 반영비율로 가중한 값으로 비교하면 **강점이 뚜렷한 학생이 체계적으로 과대평가**된다.

`ResultCut.basis` 가 입결의 산출 기준을 말해주므로, **같은 기준으로 계산한 학생 값**과
비교해야 한다. 미지정이면 `simpleAverage` 로 간주한다.

### 4.3 경쟁률·충원인원을 난이도 보정에 쓰면 안 된다

정시 경쟁률은 합격선과 **거의 무상관**이다 — 한 학생이 가·나·다군에 세 번 지원하므로
그 대학을 1지망으로 두지 않은 지원자가 섞인다.
충원인원은 70%컷에 **이미 반영**되어 있어 별도로 쓰면 이중 계산이다.

둘 다 표시용으로만 쓴다. 프롬프트에도 이 취지의 가드가 들어가 있다.

### 4.4 `referenceCut` 은 "전년도 컷"이 아니다

3개년 가중평균(0.5/0.3/0.2)에 추세·모집인원 보정까지 적용한 **기준컷**이다.
연도별 원본 컷은 `cutHistory` 에 있다.
사용자에게 보일 문구는 "3개년 기준컷"으로 쓴다.

### 4.5 `convertedScore` 가 `totalScore` 를 초과할 수 있다

`totalScore` 는 **가산점 제외 기준 만점**이다. 가산 보유 모집단위는 최대 5% 초과한다.
UI는 `convertedScore > totalScore` 를 **값 비교로** 판정해야 한다 —
`formula.bonus` 유무로 분기하면 틀린다. 한국사 가산만으로도 초과하는 케이스가 있다.

입결 컷도 같은 기준인지는 `ResultCut.bonusIncluded` 가 말해준다.
`false` 인데 학생 점수에 가산이 붙으면 **가산 수혜자만 선택적으로 과대평가**된다.

### 4.6 추천·조합이 비는 것은 정상이다

- **다군 슬롯**: 다군 모집 자체가 드물고 서울대·연고대·서성한은 다군이 없다.
  `GroupCombination` 의 `null` 을 오류로 다루지 말 것.
- **지원 불가**: 희망 계열 전체가 선택과목 제한에 걸리면 추천·조합·유리한대학이
  모두 빈다(`selection.blockedByRestrictions`). 이때 **다른 계열로 대체하지 않는다** —
  리포트가 "전공을 바꿔야 한다"는 판단을 자동으로 내리게 되기 때문이다.
  `notices` 가 사유를 설명한다.

### 4.6-0 같은 학과의 인문·자연 분리 모집

- **원천 데이터는 수정하지 않는다.** 원천(`data/source/` 의 units·formulas·bonuses 등)의 중복 행·
  조건 표기는 `scripts/jeongsi/build-engine-data.ts` 가 읽을 때 처리한다. 파생 파일
  (`admission-plans-2027.json`, `admission-results.json`, `source/engine-conversion-report.json`,
  `source/plans-without-results.json`)만 스크립트가 다시 쓴다.
- 가산점 조건 해석(`resolveBonusCondition`): 같은 가산 행이 두 번 있으면 한 번만 읽는다.
  "특성화고 … 제외"는 일반전형에 그대로 붙이고, "자연계열 지원자 과탐 응시"는 자연·의약
  모집단위에만, "○○전공 제외"는 그 모집단위만 뺀다. 그 밖의 조건(상위 영역 포함 시, 총점 합산형,
  사탐 가산 등)은 지금처럼 제외한다. 이 처리 전에는 (자연) 단위만 "가산점 유형 미지원"으로 빠지고
  (인문) 단위가 남아 자연계 학생에게 (인문) 단위가 추천됐다(경희대 한의예과, 이화여대 의예과·
  인공지능데이터사이언스학부 등 7개 학과). 재생성으로 1553 → 1636개(자연 66, 의약 17)가 됐다(이후 추정치 제외로 1294개).
- 엔진(`excludeOtherTrackSplits`): 학생 계열(미적분·기하 + 과탐 = 자연, 확통 + 사탐 = 인문,
  엇갈리면 판정 안 함)과 같은 학과의 자기 계열 단위가 있으면 반대 계열 단위를 후보에서 뺀다.
  짝이 없는 단위는 실제 교차 지원 선택지라 남긴다(예: 국민대 경영정보학부는 2027 인문 모집인원이
  미공개라 (자연)만 있다).
- **원문에 없는 값은 만들지 않는다**(사용자 결정 2026-11-04: "원문 데이터는 없으면 진짜 없는 것").
  - 전국 최고점·환산 만점이 원문에 없어 추정치(140·72 등)가 필요한 환산식은 서비스 데이터에서
    뺀다(`REASON.estimatedMax`). 1636 → 1294개. 서울대·서강대·한양대·이화여대·한국외대·아주대·
    인하대·숙명여대·전남대·경상국립대 등이 이 이유로 빠진다. 원문에 그 값이 들어오면 돌아온다.
  - 엔진은 입결이 없는 모집단위의 컷을 추정하지 않는다(대리 컷 폐기, 후보에서 뺀다). 70%컷이
    없는 해에 50%컷·평균을 보정해 쓰지 않는다(대체 컷 폐기). 그래서 "추정 기반 한 단계 하향"도 없다.
  - 스크립트가 하는 일은 원문 표기를 읽는 것뿐이다: 중복 행은 한 번만, 조건 문구는 뜻이 분명한
    것만 해석한다.
- 남은 일: 가산점 유형 미지원으로 빠진 일반전형 단위(총점 합산형, 상위 영역 포함 조건, 사탐 가산
  등)는 원문 값만으로 계산되는 형태부터 엔진을 넓히면 돌아온다.

### 4.6-a 대계열 확대는 적정이 0곳일 때, 적정 밴드에만

> 2026-11-08: 대계열 확대(Stage 3)는 없앴다. 후보는 계열그룹(Stage 2)까지만 모은다. 적정을 메우려고 넓혔더니
> 전자공학 희망 학생에게 식품영양학과·수학과가 적정 추천으로 나갔다(실측). 아래는 기록으로 남긴다.

Stage 3 후보는 적정 밴드를 메우는 데만 쓰고 상향·안정·PART 2 에는 넣지 않는다.
계열무관 모집단위도 이름에 다른 대계열이 드러나면 제외한다(`matchesNeutralPlanField`).
σ 는 3.0 을 넘지 않는다(`SIGMA_MAX`).

### 4.6-b AI 해설은 코드가 한 번 더 교정한다

`report/commentary-guards.ts` 가 AI 응답의 원서 장수(합 3장), 가중치 표기
("가중치 120%" → "가중치 120"), 고정 비율 인용("국수탐 35%씩" → 실제 영역별 비율),
라벨보다 센 가능성 표현("매우 높은"), 목록 대학 수("N곳")를 원서 장수처럼 쓴
문장을 코드값으로 고친다.
해설 첫머리 소재(PART 3 코멘트·PART 5 1문장)는 `assignRotatingTopics` 로 코드가
항목마다 돌려 배정한다. "다르게 쓰라"는 지시만으로는 같은 소재로 시작했다(실측).
PART 3 한 줄 코멘트는 모델을 거치지 않고 코드가 잇는다(`composeRecommendationComment` =
첫머리 구절 + 격차 문구 + 해석 문구). 첫머리는 "안정 3곳 중 여유가 가장 큰 곳으로",
"컷 흐름이 상승(2024 75 → 2026 82)인 곳으로", "가군 적정 원서로", "11명을 뽑는 모집단위로"
처럼 완성된 구절이다. 조각을 모델에 주고 잇게 했더니 "여유가 가장 작음으로", "보합으로 컷이
보합했고"처럼 이음새가 틀렸다(2026-11-04). PART 3 프롬프트는 총평만 요청한다.
PART 5 는 소재에 인용할 값을 붙이고 2문장 맺음말도 구분별로 돌려 배정한다.
PART 2 는 약점 영역의 실제 반영비율과 목록 안 범위를 싣는다(근거 없는 "완화" 서술 방지).
PART 4 는 조합 라벨마다 선정 기준·얻는 것·대가를 코드가 준다.
연도별 컷 흐름은 코드가 상승·하락·보합·하락 후 반등·상승 후 하락으로 판정해 싣는다
(1백분위점 미만 변화는 보합). PART 2 의 약점 영역 줄에는 목록 안 위치 판정을 싣고,
상위 영역 선택 대학은 `resolveAreaRatios` 로 이 학생에게 실제 적용되는 비율을 쓴다.
`advantageScore` 는 정렬에만 쓰고 화면·프롬프트에 숫자로 노출하지 않는다.
기준컷 대비 방향("넘겨"↔"모자라")과 크기는 `normalizeGapDirection` 이 격차 부호로 맞춘다.
영어 등급별 감점·가산 인용은 `normalizeEnglishCitation` 이 대학 정책값으로 고친다
(모델이 격차 0.4 를 "2등급 감점 0.4점" 으로 끌어다 썼다 — 실측).
PART 3 총평의 구간별 격차 범위와 "신중하게 다룰 대학", PART 2 강점·약점 비율의 목록 안 위치,
PART 5 경쟁률의 목록 안 위치는 코드가 판정해 싣는다. PART 2 첫 문장 시작 방식도 코드가 돌려 배정한다.
PART 4 의 "다른 조합과 달라지는 칸"은 `formatDistinctSlots` 가 계산해 준다(맡기면 세 칸을 나열했다).

### 4.6-d 지시보다 구조로 고정한다 (7회 생성 실측 근거)

7회 생성 결과를 규칙 검사기로 집계한 결과, JSON 키 구조는 7회 모두 지켜졌고(폴백 0건)
코드가 계산·교정한 사실도 오류가 없었다. 반면 "다르게 써라", "나열하지 마라" 같은 지시만으로는
반복과 나열이 남았고, 예시 문장은 그대로 베껴 쓰였다. 그래서 다음 원칙을 따른다.

- 문장 수는 지시 대신 JSON 구조로 고정한다. 여러 문장 필드는 문장 하나를 배열 원소 하나로 받고,
  `schemas.ts` 가 이어 붙인다(문자열로 와도 받는다).
- 학생마다 달라지지 않는 정의 문장은 코드가 쓴다. PART 4 의 선정 기준·맞바꿈 문장은
  `COMBINATION_LABEL_SENTENCES` 가 쓰고, 모델은 달라지는 칸의 해석 한 문장(`difference`)만 쓴다.
  수시 admissionPrediction 의 "정해진 문장 구조 + 해석 자리만 채우기" 방식이다.
- 예시는 구조만 보여 준다. 수치·대학명은 `<>` 자리표시로 두고 판단 방향은 학생 수치를 따르게 한다
  (Gemini 공식 가이드: 예시가 많거나 구체적이면 그대로 따라 쓴다).
- 글자 수 상한은 필수 내용의 실측 길이에 맞춘다. PART 3 코멘트는 소재·격차·정해진 해석 문구가
  들어가 실측 81~103자였으므로 110자로 둔다.
- 표 칸의 문구는 모델이 그대로 베낀다(8회차: "연도별 컷의 흐름 — …" 7곳 모두). 칸에는 그대로 옮겨도
  되는 자연어만 싣고, 남은 소재 이름은 `stripTopicLabel` 이 걷어 낸다.
- PART 4 에서 세 칸이 모두 다른 조합은 해석 문장도 코드가 쓴다(`FULLY_DISTINCT_SENTENCE`).
  "공통 성격으로 묶어 말하라" 는 지시에도 세 칸을 나열했다.
- PART 5 소재에서 경쟁률을 뺐다. 3회 연속 합격 가능성의 근거로 오독했다.
- 총평 상한을 넘긴 원인은 필수 내용이 상한보다 길었기 때문이다(PART 3 372자). 문장별 상한을
  JSON 자리에 적고, 항목 해설과 정해진 문장에 이미 있는 내용은 총평에서 다시 옮기지 않게 했다.
  9회차에서 PART 3 372→230자, PART 4 306→154자로 상한 안에 들었다. 상한을 적지 않은
  PART 2 총평은 같은 회차에 5문장 401자로 늘어, PART 2 에도 같은 틀을 적용했다.
- 항목 해설 2문장에 "목록에서 갖는 쓰임으로 맺는다"를 붙이자 PART 2 다섯 곳 모두
  "○군 지원 시 …" 절과 "<대학> <학과>는" 주어가 붙어 143~168자가 됐다(9회차). 맺음 지시를
  되돌리고, 주어는 `stripLeadingSubject` 로 걷어 낸다.
- PART 2 1문장 소재는 유리함의 근거가 되는 값만 준다(강점 비율 "가장 높음", 약점 비율
  "가장 낮음"·"빠짐", 그 밖에는 활용지표). 약점 비율이 가장 높은 대학에 약점 소재를 주자
  "부담을 줄이는 데 유리"로 방향을 뒤집었다(9회차 동국대 탐구 25%).
  응답 JSON 문자열은 `sanitizeCommentaryTone` 으로 AI 클리셰를 먼저 치환한다
  (수시 `sanitizeAiTone` 중 정시에도 맞는 항목만 옮김).

### 4.6-e 해설 검증·다시 쓰기·폴백 (`commentary-validation.ts`)

9회 생성에서 지시문에 맡긴 규칙(문장 수·글자 수·맺음)은 회차마다 다른 곳에서 깨졌다.
그래서 꼭 지켜야 하는 규칙은 리포트에 담기 전에 코드가 검사한다. 프롬프트 문구를 고쳐
막는 방식은 쓰지 않는다.

- 칸(`CommentarySlot`)마다 규칙(`TEXT_RULE`: 문장 수·글자 수, PART 3 코멘트는 정해진 해석
  문구 포함), 금지 표현, 소재 이름 복사를 검사한다. PART 2 는 약점 비율이 "가장 높음"인
  대학을 "부담을 줄여 준다"고 쓴 문장도 위반이다(`findReversedBurden`, 2회 실측).
  PART 2·3·5 항목은 약점 영역을 강점이라고 쓴 문장(`findWeaknessCalledStrength`), 모든 칸은
  "성적 관리"처럼 수능 뒤에 맞지 않는 성적 조언도 위반이다(각 1회 실측).
- 위반 칸만 원래 프롬프트에 "## 다시 쓰기"(이전 문장 + 코드가 적은 고칠 점)를 붙여 1회 다시
  요청한다(`buildRepairPrompt`). 1차 호출 자체가 실패한 파트는 다시 요청하지 않는다.
- 다시 받은 문장도 위반이면 그 칸의 확정값으로 만든 폴백을 쓴다(일반 문구 폴백은 한 리포트에
  3~4번 반복돼 원문보다 나빴다). 총평은 앞 문장들과 마지막 결론 문장을 남겨(`keepFrameSentences`,
  앞에서만 자르면 결론이 잘렸다) 규칙을 지키면 그 문장, PART 3 총평은
  `composeRecommendationOverall`, PART 3 코멘트는 `composeChanceSentence`, PART 2 해설은
  `composeMatchFallbackReason`.
- PART 5 추천 이유는 두 문장 모두 코드가 쓰고 모델을 부르지 않는다. 1문장은 배정된 소재의 판정
  문장(`composeDetailFallback`, 70자 이내), 2문장은 기준컷 격차 + 해석 문구다. 모델에 값과 판정을
  넘겼을 때 값을 주어로 세우고 판정 문장을 서술어로 이어 붙여 주어·서술어가 맞지 않는 문장이
  10명 중 다수에서 나왔다("영어 2등급과 한 등급 아래의 차 3점은 … 영향을 주는 구조입니다",
  2026-11-04). 판정 하나를 옮기는 자리라 모델이 더하는 정보가 없다.
- 수치 대조: 칸마다 인용할 수 있는 값(학생 성적 + 그 칸의 데이터·판정 문장의 수치, 소수 한 자리
  반올림 포함)을 모아(`collectNumbers`), 그 밖의 수치가 나오면 위반이다(`findUngroundedNumbers`).
  다른 대학·다른 영역의 값을 옮겨 쓰거나 지어낸 값이 리포트에 나가지 않는다. 직전 5명 실제
  해설에 돌려 보니 오탐 0건. 허용 목록만으로는 영역을 바꿔 쓴 값(국어 84 를 "영어 백분위 84")이
  통과하므로 "영역 + 백분위/표준점수 + 수치"의 짝도 실제 값과 대조한다(`findMismatchedAreaScores`).
- 대학 이름 대조: 그 칸의 데이터에 없는 "○○대학교"가 나오면 위반이다(`findForeignUniversityNames`,
  실측: 목록에 없는 "중앙대학교 경영학과"를 국민대 칸에 씀).
- PART 3 총평은 신중히 볼 곳을 대학 이름으로 밝혀야 하고(실측: "이 대학들"로 대상 없이 씀),
  PART 1 영어 강점·약점 해설에 "표준점수"가 나오면 위반이다(영어는 등급 반영).
- PART 4 총평의 "기본 배분과 같은 조합"은 코드가 칸을 세어 판정해 재료로 주고
  (`judgeCombinationAllocation`), "배분"을 말하는 문장이 지목한 조합이 그 결과와 다르면 위반이다
  (실측: 5명 중 4명이 틀린 조합을 지목).
- PART 1 강점·약점, PART 4 총평 폴백은 "해설을 생성하지 못했습니다" 안내문 대신 실제 성적·판정으로
  쓴 문장이다(`composeAreaCommentFallback`).
- 섹션 안 같은 문장: 반복은 "문장 전체가 글자까지 같은 경우"만 본다(같은 단어 재사용은 괜찮다).
  검증·폴백이 끝난 뒤 `ensureUniqueSentences` 가 섹션마다 앞 칸에 나온 문장을 그 위치의 다른
  판정 문장으로 바꾼다(PART 2 `listMatchFactSentences`, PART 5 `listDetailFacts`, PART 3·5 격차
  문장은 다른 해석 문구). 바꿀 문장이 없으면 그 문장을 빼고 로그를 남긴다. 다시 쓰기 요청으로는
  고쳐지지 않아(실측) 재요청 대상에는 넣지 않는다.
- 검증은 생성 1회로 판단하지 않는다. temperature 0 이라 같은 학생은 회차가 달라도 결과가
  같으므로(3회 실측), 회차 대신 학생을 늘려(5명: 자연·인문, 서울·수도권·전국, 성향 3종) 본다.
  최종: 5명 모두 길이·문장 수·금지 표현·해석 문구·격차 방향 위반 0, 폴백 0칸,
  리포트당 다시 쓰기 1~3회.

### 4.6-f 코드가 판정하고 모델은 문장만 쓴다 (`judged-facts.ts`)

수시 admissionPrediction 은 대학별 원시 수치를 넘기지 않고, 코드가 판정한 라벨과 해석이 담긴
문장 틀만 넘긴다. 정시도 같은 방식으로 바꿨다.

- 문장마다 "인용할 값 하나 + 그 값이 이 학생에게 갖는 의미(판정)"만 넘긴다. 판정 문장 자체가
  컨설턴트 해석이다(유리함·부담·지원 판단). 원시 수치를 통째로 넘겼을 때 모델이 쓰지 말아야 할
  값을 골랐다(모든 등급이 같은 한국사 가산점을 "부담 상쇄"로, 약점인 탐구를 "강점"으로).
- 탐구 변환표준점수표는 학생이 응시한 과목의 열을 쓴다(2026-11-08). 사탐·과탐 열이 같으면
  `formula.convertedStandardTable` 하나, 다르면 `formula.convertedStandardTableByTrack {science, social}`
  에 두 열을 모두 싣고 엔진이 과목마다 `convertedTableFor(formula, subject)` 로 고른다. 이전에는 모집단위
  계열(인문·자연)로 열 하나를 골라 사탐 응시자에게 과탐 열 점수를 줄 수 있었다(전북대). 원문에 "해당없음"인
  열은 null 이고, 반영할 과목이 모자라면 지원 불가로 분류한다(`lacksConvertibleInquiry`). 열마다 최고점이
  달라 "변표 최고점으로 나누는" 분모가 과목에 따라 달라지는 비율형 환산식은 뺀다(사유
  "사탐·과탐 변표 최고점이 달라 환산 분모를 원문으로 정할 수 없음", 62개). 가중치형은 비중 추정 표시.
- 2027학년도 환산식이 가리키는 변환표는 원천 데이터 자체가 2026학년도 표(…-TAM-2026)로 연결해 두었다
  (2027 환산식 201개 전부). 엔진은 원문 연결을 그대로 따른다 — 엔진이 연도를 바꿔 고르는 것이 아니다.
- 백분위 입결은 탐구 처리가 원문에 "2과목 평균"으로 적힌 것만 쓴다(2026-11-08). 이전에는 "미공개"를
  2과목 평균으로 간주해 썼다(원문 5,787행). 이로써 입결이 모두 사라진 161개 모집단위가 빠졌고(가톨릭관동대
  전체 포함, 1294 → 1143), 남은 모집단위 중 484개는 쓸 수 있는 입결 연도가 줄었다.
- 백분위→표준점수 기울기표는 폐기했다(2026-11-05). 민감도는 백분위만 1점 올린 환산점수 변화로 구하고,
  표준점수 반영 대학은 null 이다(`calcSensitivity`). 그런 대학의 환산점수 입결은 비교할 수 없는 컷이고
  (현재 0건), PART 5 등급 손실의 "백분위 약 X점 상당" 판정도 쓰지 않는다.
- 가중치 공시 + 표준점수 반영 대학(고려대·연세대·경북대 183개)은 비중(%)이 추정값이라
  `plan.areaSharesEstimated` 로 표시한다. 유리도 기본 점수 50, 가중 백분위 null, PART 5 비중 판정 없음.
  PART 2 가중치 판정은 같은 지표(척도)인 영역끼리만 견주고, 영역마다 지표가 다르면 "백분위로 반영"이라
  쓰지 않는다(`metricFactOf`).
- 리포트 구성(입시*분석*기능\_정보/report_template.png)에 맞춰 해설 관점을 정했다(2026-11-08).
  - PART 1 = 현재 성적 수준 + 영역별 강점·약점. 총평 1문장은 성적 수준으로, 백분위의 정의대로
    "응시자 상위 약 N%"를 쓴다(`describeAreaLevel`, 추정 아님; 탐구는 과목별). 2문장 영역 간 구조, 3문장 지원에서의 의미.
  - PART 2 = 컨설턴트 관점. 모델이 쓴 근거 두 문장 뒤에 코드가 판단 문장을 붙인다(`composeMatchVerdicts`:
    강점 비중 최대·약점 제외/최소 → 유리, 약점 비중 최대·유일 반영 → 주의, 그 밖 → 중립).
  - PART 5 추천 이유 = 반영방식 판정 + 격차·합격 가능성 + 원서 운용 조언(`composeDetailAdvice`, 구분·모집군 기준).
- 영어는 원문에 등급만 있어 백분위·순위·편차를 만들지 않는다(사용자 결정 2026-11-05). PART 1 순위·편차·
  강점·약점, 유리도 기본 점수, 가중 백분위는 국어·수학·탐구로 계산한다. 영어는 대학별 등급 감점·점수표로만
  다룬다. PART 1 문장이 영어를 백분위·표준점수로 쓰면 위반이다(`findEnglishPercentile`).
- 강점·약점이 여럿이면 엔진이 편차가 큰 영역부터 담는다(`pickStrengths`·`pickWeaknesses`). 리포트는 첫 영역을
  대표로 쓰는데, 영역 순서 그대로였을 때 수학 52점보다 국어 66점이 대표 약점이 됐다(2026-11-04).
- 판정: PART 1 영역 간 백분위 차이(5점 기준, 국어·수학·탐구), PART 2 목록 안 강점·약점 비중
  위치와 같은 재료를 쓰는 대학의 선택 기준, PART 3 구분별 곳 수·성향 배분·신중히 볼 곳,
  PART 5 반영비율·가산점(학생에게 적용되는 것만)·영어/한국사 손실(백분위점으로 환산해 그 대학의
  기준컷 대비 격차와 비교)·활용지표. PART 5 소재는 판정 문장이 겹치지 않게, 덜 쓴 종류부터 고른다.
- PART 3 표는 격차 수치 대신 코드가 쓴 격차 문구를 싣는다(수치를 주자 "기준컷을 -1.3 모자라").
  대학명·환산점수 열은 뺐다(실었더니 문장에 끼워 넣었다).
- 판정마다 코드 문장(`sentence`)이 있고, AI 문장이 규칙을 어기거나 비어 있으면 그 문장을 쓴다.
  폴백도 해석을 담는다. 폴백을 쓰면 `[jeongsi:report] … 폴백 적용` 로그를 남긴다.
- 프롬프트는 긍정 지시와 긍정 예시만 쓴다. 다시 쓰기 요청에도 이전 문장을 싣지 않는다(낮은
  모델은 보여 준 문장을 따라 쓴다). 예시의 판단 자리는 `<판단>` 빈칸으로 둔다 — 판단까지 적은
  예시를 그대로 베꼈다(실측: 재료는 "상향 없음"인데 예시의 "1곳뿐"을 씀).
- 숫자 뒤 조사(`normalizeNumberParticles`)는 모든 가드 뒤에 맞춘다.
- 측정(학생 5명): 규칙 위반 0건, 폴백 8칸(PART 2 120자 초과 6, PART 3 총평 300자 초과 2).
- PART 5 반복 대응: 영어가 강점이면 "손실 없음" 대신 한 등급 아래보다 앞서는 점수를 백분위점으로
  환산해 그 대학의 격차와 견준다(대학마다 다름). 같은 종류 판정이 이어지면 같은 뜻의 두 문장 틀을
  번갈아 쓴다. 영어 1등급 학생의 PART 5 같은 문장이 9곳 중 5곳 → 2곳으로 줄었다.
- PART 2 반복 대응: 같은 판정이 두 번째부터 나오면 프롬프트에 같은 뜻의 다른 문장(`alternate`)을
  준다. 반영비율이 같은 앞 대학이 있으면 2문장은 둘 사이의 선택 기준이다. "○○와 같은 … 조건이라"로
  앞 대학을 줄줄이 가리키는 방식은 기계적으로 읽혀 뺐고, 남는 똑같은 문장은 위
  `ensureUniqueSentences` 가 바꾼다(직전 5명의 5쌍 → 0쌍). 바꿀 문장은 그 위치 판정의 다른 표현을
  먼저, 그다음 다른 위치가 쓰지 않는 판정을 쓴다(다른 위치의 판정을 쓰면 한 항목 안에서 같은 뜻이
  두 번 나왔다).
- 목록에서 그 영역을 반영하는 대학이 하나뿐이면(position null) "목록 대학과 같다"가 아니라
  "이곳뿐"으로 판정한다(실측: 서울여대 수학 15%, 다른 대학은 모두 0%).
- PART 2 강점 판정의 성적은 그 영역의 값을 쓴다. 영어는 등급으로 쓴다(실측: 영어 강점에 국어
  백분위 84).
- PART 3 같은 구분 안 위치: 기준컷에 못 미친 곳은 "여유" 대신 컷과의 거리로 말한다.
- 다른 유형 학생 5명(사탐 자연 지망, 의대, 체육교육, 지원 가능 목록 없음, 계열 지원)으로 찾은 것:
  - 목록이 빈 파트(PART 2·3·4)는 호출하지 않고 총평을 코드가 쓴다. 모델에 맡기면 없는 목록을
    설명했다("목록 대학들은 모두 영어 반영 비율이 높아", "모든 대학이 기준컷 이상"). 응시 과목
    제한으로 비었으면 안내 문구와 같은 이유("현재 응시 과목 조건")로 말한다.
  - 강점·약점 비중 판정이 없는 가중치 대학은 2문장을 가중치 판정으로 쓴다(`judgeMatchWeight`,
    두 문장이 같은 판정이던 고려대 의예과). 같은 판정이 세 곳 이상이면 `extraSentences` 로 표현을 더 둔다.
  - 영어 1등급이 순위로만 약점이면 "환산 손실"은 틀린 정보다. 위반으로 보고 폴백은 "잃는 점수가
    없다"로 쓴다.
  - "0% 반영하지 않는"(이중 부정)은 가드가 수치를 뗀다. 학과명이 "과"로 끝나도 주어로 뗀다.
  - PART 3 컷 흐름은 이제 코드가 판정 그대로 쓴다(이전의 `findTrendContradiction` 검사는 없앴다).
  - 엔진이 더한 "<라벨> 대안" 조합도 선정 기준·맞바꿈 문장을 갖는다(맞바꿈은 원래 조합과 다른 문장).
- PART 4 차이 문장 폴백은 다른 조합과 갈리는 칸을 짚어 조합마다 다르게 쓴다
  (`composeDifferenceFallback`, 일반 문구 하나면 세 조합에 같은 문장이 반복된다).

### 4.6-c 합격 가능성 표현과 문장 기법은 수시 프롬프트를 따른다

합격 가능성은 `system-prompt.ts` `JEONGSI_CHANCE_PHRASES` 의 정해진 문구만 쓴다.
라벨은 수시 admissionPrediction 4단계("합격가능성이 있는 구간" / "지원은 가능한 구간" /
"합격이 어려울 수 있는 구간" / "지원을 권장하지 않는 구간")와 같고, 높음·보통·낮음·매우낮음에
대응한다. 항목 해설(PART 3 코멘트·PART 5 2문장)은 `assignChanceMeanings` 가 배정한 해석
문구로 코드가 맺고(배지가 라벨을 보여 주므로 라벨은 다시 쓰지 않는다), 총평은 같은 라벨의 대학을
묶어 라벨을 인용한다(PART 3 3문장, 수시의 "분류 통계" 마무리 방식).
"소신 지원·안전판·○○ 카드" 같은 짧은 분류 표현은 쓰지 않는다(수시 규칙).
해설 원칙도 수시 system.ts 를 따른다: 모든 문장에 컨설턴트 판단("So What" 질문 4개),
수치 인용은 근거로 짧게(해석 80% 이상), 표면 해석에서 한 단계 더(목록 내 위치·원서 배치),
유리한 점과 주의할 점을 함께 쓰고 결론은 한 방향, 주의 표현 강도는 합격 가능성 라벨에 맞춤.
파트마다 `PART_PERSPECTIVES` 로 서술 관점과 다른 파트의 범위를 나눠 파트 간 반복을 줄인다.
PART 1 약점 해설은 현재 위치 → 원인 → 왜 중요한가 → 대응 흐름(수시 컨설팅 서술 구조).
그 밖에 수시에서 옮긴 기법: 문장 패턴 6종 섞기, 섹션별 출력 전 자가 점검,
PART 4 첫 문장 시작 방식 코드 배정과 "얻는 것 대신 대가" 문장, 120자 넘는 문장 나누기.

### 4.7 면허·자격 연계 트랙은 대계열 확대 금지

의약·보건·교육학은 학과 전환이 자유롭지 않아, 계열그룹을 넘는 추천이 쓸모없다.
간호 지망생 추천에 전자공학과가 들어오면 안 된다.
추천 3개를 못 채워도 그대로 둔다 — **관련 있고 불완전한 추천이 완전하고 무관한 추천보다 낫다.**

### 6.1 엔진에 들어간 것은 일부다 — 의도된 것이다

원본 15,160 모집단위 중 **1,811 (87개 대학)** 만 엔진 JSON 에 들어간다.

정확히 재현할 수 있는 일반전형만 옮기고, 나머지는 사유를 `engine-conversion-report.json`
의 `excludedByReason` / `excludedUnits` 에 남긴다. 큰 사유는 특별전형(6,992)·2027 미모집(2,708)·
가산점 유형 미지원(637)·기본점수 상수(478)·**상위 영역 선택 규칙 미지원(448)** 이다.

검증 장치 두 가지:

- `data/__tests__/official-examples.test.ts` — 대학 공식 계산예시 18건 재현 (상위 영역 선택 11건 포함)

  표준점수형은 가상 학생의 표준점수 추정 오차가 섞여 있다)

> 🔴 공개 입결이 없는 모집단위는 시행계획에서 뺀다(013 §6.1-a1). 제외분은 환산식 회귀 테스트용
> `data/source/plans-without-results.json` 에만 남고 서비스는 읽지 않는다.

### 6.2 엔진 계약에 생긴 변화

- `JeongsiResultEntry.competitionRate` 선택값 — 실데이터 경쟁률 미공개가 있다
- `JeongsiAdmissionPlan.suneungWeight` — 수능 80% 이상 전형(서울대 80·연세대 95·중앙대 90 등)을
  넣고, 수능만으로 계산한 위치임을 표시한다. 이 모집단위는 수능 기준 입결만 비교한다
- `BonusPolicy.scienceInquiry.minCount` — "과탐 2과목 응시 시" 가산
- `baseMax` 는 "지표 만점"이 아니라 **정규화 분모**다. ÷200 대학은 200, 가중치형 대학은
  계수를 맞추기 위한 값이 들어간다. 백분위라고 100 이라는 보장이 없다
- 영어 가산형(`english.type = "add"`)은 `ratios.english` 가 0 일 수 있다(가산이 만점 위에 얹히는 대학)
- 리포트 PART 3·5 항목의 `cutComparison` — 실데이터 입결은 대부분 **백분위** 컷이라, 환산점수 옆에 컷을
  숫자만 두면 단위가 어긋난다. 컷 지표·같은 지표의 학생 값·3개년 기준컷·전년도 실제 컷을 싣고, 화면·프롬프트는
  `report/cut-format.ts` 로 단위를 붙인다. 필드가 없는 예전 리포트는 환산점수 기준으로 복원한다 (013 §6.2)
- PART 4 조합은 템플릿대로 **3~5개** (차별화 축 4개 + 대안). 013 §4.5

### 6.2.1 상위 영역 선택 반영 (`ConversionFormula.selection`)

"국·수 중 우수 영역 45%, 다른 영역 35%"(서강대·가톨릭대), "국·수·영·탐 중 상위 3개 영역 평균"
(교통대·금오공대) 같은 반영방식이다. 413 모집단위(40개 대학)가 이 규칙을 쓴다.

- 엔진은 `resolveAreaRatios(score, formula)` 로 학생 순위에 따른 **실제 반영비율**을 만든다.
  환산점수·민감도·영어 손실이 이 값을 쓴다. 비중을 분석·해설에 쓸 때는 `resolveAreaShares(score, plan)`
  을 쓴다 — 비중을 추정치로 역산한 대학(`plan.areaSharesEstimated`)은 null 이다.
  `formula.ratios` 를 직접 읽는 코드를 새로 만들지 말 것 — 선택 대상 영역 값은 자리값이다
- 순위 비교 기준(`rankBasis`): 표준점수 / 백분위 / 영역 환산점수. 영어는 대학의 영어 점수표(원문)를
  100점 기준으로 맞춰 비교한다. 점수표가 없으면 영어는 선택 대상이 되지 않는다
- 변환기는 원본 `selection` 칸(targets·count·rankRatios·rankBasis)을 옮기고, 한국사·제2외국어가
  후보이거나, 탐구 과목 단위 선택, 가산점 포함 순위, 중첩 선택("1순위 제외 … 중")은 제외한다
- `33.33` 은 1/3 로 되돌린다. 단 산출식이 `0.3333` 을 그대로 곱하는 대학(금오공대·경일대)은 그대로 둔다
- 변환 리포트 `consistency` 는 이 대학들에서 **음수로 치우친다**. 가상 학생은 전 영역 백분위가
  같아서, 강점 영역만 골라 반영받는 실제 합격자보다 환산점수가 낮게 나온다. 공식 예시로 검증한다
- 백분위 입결은 대학어디가 국·수·탐 단순평균이라 선택 반영 이득이 반영되지 않는다.
  환산점수 입결이 있으면 그쪽이 더 정확하다

### 6.3 실데이터 전환 후 남은 일
